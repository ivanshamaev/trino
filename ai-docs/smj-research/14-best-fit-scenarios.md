# 14. Сценарии применимости SMJ: когда выбирать Sorted Merge Join

Ответ на два вопроса: (1) какие сценарии лучше всего подходят для SMJ (включая «две Iceberg
таблицы с одинаковым бакетированием и сортировкой»); (2) какие варианты хорошо подходят для
join 15 млрд × 17 млрд строк при заведомо недостаточной памяти для hash join.
Основано на документах 11 (сценарии exchange), 12-13 (сортировка/масштаб), risks/ (ограничения).

## 14.1. Иерархия сценариев: от идеального к худшему

Ранг определяется «ценой подготовки данных к merge»: **exchange (сеть) + сортировка (CPU/I/O) +
хэш-таблица (память)**. SMJ выгоднее всего там, где первые две компоненты дешевы, а третья
(память hash) была бы запретительной.

### 🥇 S1-GOLD: обе таблицы `bucket(k, N)` + `sorted_by(k)`, одинаковые N и sort order

«Две Iceberg таблицы с одинаковым бакетированием и сортировкой» — **да, это идеальный сценарий,
лучший из возможных**:

| Компонента | Стоимость |
|---|---|
| Exchange | **ноль** — co-located сканы (bucket execution: одинаковые handle, single spec) |
| Сортировка | **ноль пересортировки** — каждый data-файл уже отсортированный run (per-file, см. risks/01 §1.5); k-way merge сплитов бакета |
| Хэш-таблица | **ноль** |
| Память | k курсоров файлов + 1 страница на вход + окно текущей группы равных ключей |
| Сеть | только чтение данных из хранилища (S3/HDFS) |

Выполнение = **чистый стриминг**: `merge(files_bucket_L) ⋈ merge(files_bucket_R)` по каждому бакету,
десятки млрд строк проходят при памяти порядка мегабайт на драйвер (плюс окно групп). Это
единственный сценарий, где SMJ **строго доминирует** hash join по всем осям одновременно
(CPU-sequential vs random-lookup, память ~0, отказоустойчивость к skew входов).

**Условия корректности** (все обязательны, проверяются планировщиком):
- `bucket_execution_enabled=true`; ровно **одна** партиционная спека у каждой таблицы;
- **обе таблицы в одном каталоге** — `getCommonPartitioning` требует равенства `catalogHandle`
  (разные каталоги = никогда не ко-локуются, даже с одинаковыми бакетами);
- одинаковые bucket count и трансформ на join-колонке (handle `equals` — разные N не совместимы);
- все файлы снапшота с текущим `sortOrderId` (**file-level**, из манифеста — legacy 0 → fast-path
  отказывается, но SMJ остаётся доступен через обычную сортировку);
- sort order покрывает **все** equi-ключи (или ключи — префикс сортировки: sorted by (a,b) ⊇ join by (a));
- identity-трансформы в sort order (truncate/bucket в sort — не поддерживаются);
- join-ключи — сырые колонки (cast ломает вывод sortedness).

### 🥈 S2: обе `bucket(k, N)`, но **не** сортированы

Co-location без exchange; каждая сторона сортируется локально (внешняя сортировка со спиллом —
объём = данные бакета). Стоимость = один проход write+read по диску на сторону. Всё ещё сильно
лучше hash при большом build: хэш-таблица 17 млрд строк не влезает никуда, а сортировка — линейна
по I/O. Оптимален при повторяющихся join'ах по одному ключу (можно даже CLUSTER BY при записи).

### 🥉 S3: одна сторона `bucket(k, N)`, вторая нет

Shuffle только неподбакеченной стороны — **в bucket-функцию первой** (AddExches.planPartitionedJoin).
Половина сетевой цены полного shuffle. Бакетированная сторона сортируется на сканах (per-file
runs), вторая — после exchange.

### S4: обе без бакетов (полный shuffle + sort)

Классический Spark-путь: repartition обеих по k, локальная внешняя сортировка, merge. Самый
дорогой вход, но **единственный жизнеспособный** при build, не влезающем в память (15B×17B).
Сравнение с grace-hash — §14.3.

### S5: сортированы, но НЕ бакетированы

⚠️ **Ловушка ожиданий**: сортировка без координации бакетов не помогает — repartition по ключу
ломает порядок, сортировать придётся заново. Выигрыш остаётся только если сортировка «дёшево
восстановима» — future: range-partitioning exchange по Iceberg min/max (ClickHouse PK-ranges-паттерн).
Сегодня: трактовать как S4.

## 14.2. Когда SMJ выбирать даже при сортировке «в холостую» (S4): сигналы

Для 15B×17B с заведомо малой памятью SMJ (S4) — правильный выбор, если выполняется любое из:

1. **Build-сторона > ~1.5-2× доступной памяти на задачу** — hash join обречён на многократный
   spill-проход (перестройка LookupSource, повторное чтение probe), SMJ даёт ровно 1 write+1 read.
2. **Нужен RIGHT/FULL OUTER** — у Trino hash join build-outer **не спиллится вообще** (AddExchanges
   инвариант + spilling-ограничение); SMJ symmetric по сторонам.
3. **Ключи с высокой NDV** (near-unique: reconciliation/dedup/upsert-слияния, ключи транзакций) —
   группы малы, вывод линеен; худший случай hash (гигантская хэш-таблица) = лучший случай SMJ.
4. **Downstream выигрывает от отсортированного вывода**: SMJ эмитит по ключу →
   - `GROUP BY` по тому же ключу → streaming-агрегация без хэш-таблицы;
   - window `PARTITION BY` тот же ключ → без сортировки окна;
   - `INSERT INTO ... sorted_by(k)` / запись в bucketed+sorted таблицу → следующее поколение
     join'ов попадает в S1-GOLD («самоусиливающийся» ETL-паттерн: SMJ сегодня — бесплатно
     отсортированные таблицы завтра).
5. **Несколько join'ов по одному ключу в цепочке** — сортировка амортизируется: sort once, merge many.
6. **Стабильность/ETL-SLA важнее пикового CPU** — предсказуемый I/O-профиль SMJ vs
   memory-churn спиллящегося hash.
7. **Мало spill-места на воркерах, но data → диск и так пишется** (write-heavy ETL): SMJ и так
   пишет результат — спилл-раны переиспользуют тот же диск-бюджет.

Анти-сигналы (оставаться на hash): build влезает в память (LLC-эффект), есть broadcast-вариант,
ключи типа MAP (не orderable), NaN-ключи до встроенного guard (risks/01 §1.1), очень низкая NDV
(взрыв вывода — проблема любого алгоритма, но SMJ не спасает ничем).

## 14.3. SMJ vs Grace Hash Join для 15B×17B (взаимодополнение, не конкуренция)

Grace hash (рекурсивное разбиение до влезания в память → hash join на партицию; в Trino
приближение — текущий spilling hash join; в ClickHouse — `grace_hash`):

| Ось | SMJ (S4) | Grace hash |
|---|---|---|
| Дисковый I/O | 1 write + 1 read на сторону (fusion), гарантированно | 1 проход разбиения + риск рекурсии (переполнение партиции → повторное разбиение) |
| CPU на вход | N log N сравнений (или radix O(N)) | N хэшей + повторные хэши при рекурсии |
| CPU на матч | sequential merge (prefetch-friendly) | random lookup в хэш-таблицу партиции |
| Память | окно группы + k буферов | партиция build (гарантированно влезает после разбиения) |
| Skew ключей | окно группы (bounded, спиллится) | горячая партиция → рекурсия → худший случай |
| Отсортированный вывод | ✅ (бонусы §14.2-4) | ❌ |
| RIGHT/FULL | ✅ симметрично | ✅ |
| Требования к типам | orderable (без MAP, NaN-guard) | любые хэшируемые |

**Рекомендация**: SMJ как основной механизм для 15B×17B при любом из сигналов §14.2; grace hash
остаётся fallback-семантикой текущего spilling hash join и не требует разработки. Cost-порог из
фазы 3: `SMJ если build_bytes > 1.5-2 × available_memory_задачи ИЛИ входы отсортированы`.

## 14.4. Практические рецепты («как готовить данные»)

### Рецепт A — золотой ETL-паттерн (максимальная скорость повторных join'ов)

```sql
-- одна схема для всех таблиц домена:
CREATE TABLE events  (..., user_id BIGINT, ...) WITH (
  partitioning = ARRAY['bucket(user_id, 256)'],   -- одинаковый N на ВСЕ таблицы домена!
  sorted_by = ARRAY['user_id'],                    -- identity-поле = join-ключ
  format_version = 2
);
CREATE TABLE profile (..., user_id BIGINT, ...) WITH ( /* те же bucket/sorted_by */ );
-- join: SELECT ... FROM events e JOIN profile p ON e.user_id = p.user_id;
-- ⇒ S1-GOLD: ноль exchange, ноль сортировки, ноль хэш-таблиц, стриминг-merge
```
Грабли: N одинаковый на ВСЕ join-имые таблицы (разные N не координируются); одна спека (эволюция
партиционирования ломает bucket execution); `sorted_by` по join-ключу (не по чему-то ещё);
документировать в team-стандарте.

### Рецепт B — большой ad-hoc join (несортированные таблицы)

`SET SESSION join_algorithm = 'MERGE'` (или FORCE-режим), пресет конфигурации из
[13, §13.9](13-case-study-15b-join-17b.md): спилл on + NVMe + LZ4, лимиты спилла ≥ данных,
`query.max-memory` кластерно поднят, `query_max_hash_partition_count = 200-400`.
Проверить сигналы §14.2; для near-unique ключей — ожидание ~1 write+1 read на сторону.

### Рецепт C — join с самособой / reconciliation (near-unique ключи)

Идеален для SMJ при любом раскладе партиционирования: группы ≈ 1 строка, вывод линеен,
хэш-таблица 17 млрд строк была бы фатальной. Типовые задачи: дедупликация, сверка двух снапшотов
(`table_changes`, CDC-слияния), anti/semi проверки существования (semi — фаза 4).

### Рецепт D — цепочка join + агрегация/окна по одному ключу

`JOIN по k → GROUP BY k`: SMJ выдаёт отсортированность. ⚠️ Поправка верификации: **streaming-агрегации
по отсортированному входу в Trino сегодня НЕТ** (grep: `preGrouped*` есть только у WindowOperator;
`streaming_aggregation_enabled` — это PrestoDB order-based execution, не Trino) — выгода для GROUP BY
**потенциальная будущая оптимизация** (можно сделать по образцу PrestoDB: streaming-группировка
отсортированного потока без хэш-таблицы — естественное продолжение SMJ). Реальные выгоды сегодня:
- **Window `PARTITION BY k`**: `WindowOperator` умеет pre-grouped/pre-sorted входы
  (`preGroupedChannels`/`preSortedChannelPrefix`) — при пробросе SortingProperty через
  `PropertyDerivations.visitJoin` (фаза 2/3) окно не пересортирует;
- **сортированная запись** `INSERT INTO ... sorted_by(k)` — вывод уже упорядочен;
- один sort кормит весь конвейер (сортировка амортизируется по цепочке операторов).

## 14.5. Сводная матрица выбора

| Сценарий | exchange | сортировка | вердикт для 15B×17B |
|---|---|---|---|
| bucket+sorted, same N (S1-GOLD) | 0 | 0 (merge файлов) | **SMJ безусловно** |
| bucket same N, unsorted (S2) | 0 | 1 write+1 read | **SMJ безусловно** (hash упирается в память) |
| bucket с одной стороны (S3) | ½ | обе стороны | **SMJ** при сигналах §14.2 |
| ничего (S4) + near-unique ключи | полн. | обе | **SMJ** (лучший выбор при малой памяти) |
| ничего (S4) + низкая NDV | полн. | обе | ⚠️ вывод взорвётся у любого алгоритма; SMJ не спасает |
| sorted без bucket (S5) | полн. | заново | сегодня = S4; future range-partitioning |
| build влезает в память | — | — | hash join (LLC), SMJ не включать |
| broadcast возможен | — | — | broadcast hash |

Итог: **«одинаковое бакетирование + одинаковая сортировка» — да, идеальный сценарий SMJ**
(ноль exchange/сортировки/памяти), а при 15B×17B и заведомо малой памяти SMJ — правильный выбор
для S2-S4 при near-unique ключах, RIGHT/FULL, цепочках с агрегацией/сортированной записью,
и как генератор S1-GOLD-таблиц для будущих запросов.
