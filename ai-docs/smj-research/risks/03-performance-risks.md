# 03. Риски производительности SMJ

Класс рисков: SMJ корректен, но **медленнее ожидаемого / медленнее hash join** в сценариях,
где его включили. Часть уже разобрана в 12/13 — здесь систематизация + новые детали.

## 3.1. 🟠 P1: Параллелизм join-стадии (главный масштабный риск)

Факты: join-стадия FIXED_HASH → задач = числу hash-партиций; `query.max-hash-partition-count=100`
(default); `DeterminePartitionCount` упрётся в 100; merge-драйвер = 1/задачу (MVP). На 50 воркерах
это 2 потока на 32-ядерной машине — сортировка/merge упрутся в параллелизм, а не в I/O.

**Решения**: (а) документированный ETL-пресет `query_max_hash_partition_count=200-400`;
(б) фаза 2: `partitionCount = k×taskCount` + per-partition merge-драйверы (реестр мостов по
instance-index); (в) фаза 3: partialSort на скан-стадиях (сортировка распараллелена сплитами,
join-задача только мержит) — тогда параллелизм join-стадии менее критичен; (г) мониторинг:
`WallClock/задачу` vs `CPU/задачу` в статистиках.

## 3.2. 🟡 P2: Деградация k-way merge на сотнях входов

`WorkProcessorUtils.mergeSorted` — единая `PriorityQueue`: boxing элементов-обёрток, log₂k на
элемент, аллокации. При 100+ ранах и 100+ файлах в бакете (sorted Iceberg!) константы съедают выгоды.

**Решения**: (а) каскад с fan-in ≤ 64 (образец — Hive `SortingFileWriter.combineFiles`, перенести
в core); (б) для k=2 (SMJ с одним раном на сторону) — прямой двухпутёвый цикл без кучи;
(в) loser-tree для больших k; (г) бенчмарк-гейт: merge при k∈{2,8,32,128,512} — планка деградации
< 20% на k=128 vs k=8.

## 3.3. 🟡 P3: Копирование вывода через PageBuilder

Существующий путь (`OrderByOperator.getSortedPages` и `MergeSortedPages`) копирует строки в новые
страницы — полный дубль байтов payload на каждый отсортированный вывод. Для sort-join fusion это
лишний проход по всему объёму.

**Решения**: (а) словарная сборка (dictionary поверх исходных страниц) — см. риск I6 (memory-учёт);
(б) fusion: merge-join потребляет `PageWithPosition`-курсоры напрямую (без сборки промежуточных
страниц) — вывод строит сам join (словари для probe-каналов как у `LookupJoinPageBuilder`);
(в) метрика «bytes copied vs referenced» в статистиках.

## 3.4. 🟠 P4: I/O-амплитфикация при re-iterate спиленных групп

Урок Spark SPARK-30536: при спиленной правой группе каждая левая строка группы может тянуть
перечитывание спилла → I/O = O(L×R) вместо O(L+R).

**Решения**: (а) block nested loop — правое окно чанками по C строк, левое окно буферизуется,
I/O = O(R + L×R/C); (б) ленивая инициализация spill-читателя (не открывать, пока не понадобится
второй проход); (в) порог: если правая группа ≤ порога (память) — вообще без спилла; (г) тест:
группа 10M×10M с лимитом памяти 64 МБ — измерить bytes-read.

## 3.5. P5: «Холодный» SMJ vs «тёплый» hash (LLC-эффект)

При данных, влезающих в LLC, hash-join непобедим (один lookup без сортировки); SMJ платит
N log N даже на мизере. Cost-модель обязана это знать (порог по размеру build vs памяти);
FORCE-режим — только для тестов. Гейт CBO-фазы: на TPC-DS SF-100 cost-режим выбирает SMJ
исключительно в big-big join'ах — план-диффы reviewed.

## 3.6. 🟠 P6: Конфиг-дефолты непригодны для BIG join (повтор из 13, как риск поставки)

Default: `spill-enabled=false`, спилл-пути не заданы, `spill-compression=NONE`,
`max-spill-per-node=100GB`, `query.max-memory=20GB` (кластерно!), exchange-компрессия `NONE`.
SMJ-ETL на 15B×17B с дефолтами **не взлетит** (даже не включится спилл).

**Решение**: документированный ETL-пресет (13, §13.9) + опциональный warning в QueryMonitor при
SMJ-плане без включённого спилла («SMJ chosen for large build but spill is disabled — expect failure»).

## 3.7. 🟡 P7: Ложные ожидания от «sorted» таблиц

Sorted-but-not-bucketed: shuffle ломает порядок → сортировка всё равно нужна. Многие пользователи
ожидают «таблица отсортирована → join быстрый». Без bucket-координации этого не будет.

**Решения**: (а) документация: выигрыш даёт **bucket(k,N)+sorted(k)** на обеих сторонах с
одинаковыми N; (б) EXPLAIN-аннотации почему SMJ не выбран («inputs sorted but not co-located»);
(в) future: range-partitioning exchange по Iceberg min/max (ClickHouse PK-ranges-паттерн) —
снимает требование bucket-координации для sorted-таблиц.

## 3.8. P8: Спилл на сетевых томах

Если spill-пути — EBS/сетевые NFS (частое облако-заблуждение), «последовательные» раны дают
100-200 МБ/с вместо 2 ГБ/с → фаза спилла удлиняется в 10×. Митигация: документация + runtime-метрика
`spillThroughput` с warning при < 500 МБ/с.

## 3.9. P9: Merge-драйвер однопоточен

Один merge-драйвер = k курсоров + join-логика + сборка вывода в одном потоке. При 200-400 партициях
это ок (параллелизм между задачами), но для single-hot-partition историй (несколько гигантских
групп) поток станет узким местом. Future: MergePath-декомпозиция merge внутри драйвера (разбить слияние
на независимые интервалы) — не в MVP, задел в статистике (queue-time драйвера).

## 3.10. P10: Деградация от PagePartitioner-порядка при shuffle

После REPARTITION строки приходят в «почти-сгруппированном» по хэшу порядке (отправители пишут
последовательно) — потенциально «адаптивная» выгода для сортировки (частично упорядоченные данные),
но quicksort на почти-сортированных с повторами не деградирует (3-way partition спасает от
duplicate-хвоста). Зафиксировать бенчмарком; Timsort НЕ нужен (см. 12, «чего не делать»).
