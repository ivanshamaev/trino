# 06. Риски: NULL-ключи и гигантский NULL-хвост (C9)

Контекст вопроса: 15 млрд строк, в join-ключе — огромный NULL-хвост. Пойдут ли все NULL в один
бакет/воркер и вызовут ли локальный OOM при слиянии, либо их нужно отфильтровать/распределить
заранее?

## 6.1. Факт 1: NULL уже сегодня идёт в ОДНУ партицию (hash join и бакетирование)

`BlockTypeOperators.BlockPositionHashCode.hashCodeNullSafe`
(core/trino-main/src/main/java/io/trino/type/BlockTypeOperators.java, ~:101-107):

```java
default long hashCodeNullSafe(Block block, int position)
{
    if (block.isNull(position)) {
        return NULL_HASH_CODE;   // константа для ЛЮБОГО null-значения
    }
    return hashCode(block, position);
}
```

Следствия:
- **Hash join**: все строки с NULL в ключе хэшируются одинаково → весь NULL-хвост падает в
  **одну build-партицию** одного воркера. Гигантский NULL-хвост = гигантская партиция — риск
  OOM/спилла существует у hash join **уже сегодня**, SMJ его не изобретает.
- **Iceberg bucket(k, N)**: bucket-функция детерминирована от хэша значения → все NULL-ключи
  в **одном бакете** одной таблицы. Co-location это не ломает (бакеты обеих сторон совпадают),
  но концентрирует NULL-хвост на одном воркере.

## 6.2. Факт 2: семантика NULL в SMJ — зеркальный аналог NaN (C1)

С каноническим `ASC NULLS_LAST` NULL-хвост — **последняя группа** на каждой стороне
(при NULLS_FIRST — первая; канонизация §4.9 плана фиксирует NULLS_LAST):

- компаратор сортировки ставит NULL-ключи рядом, сравнение NULL vs NULL = «равные позиции»;
- join-равенство: `NULL = NULL` → **false** (SQL) — NULL-группы **никогда не матчятся**.

Это та же дивергенция «compare=0, equal=false», что и C1-NaN, но с важным отличием:
**NULL-случай разрешим безопасно** — группа не может дать ни одной строки INNER-вывода.

## 6.3. 🔴 C9: наивная буферизация NULL-группы → OOM

Наивный merge-оператор, увидев «совпадение» NULL-групп (compare==0), загрузит правую
NULL-группу в MatchBuffer → при хвосте в миллиарды строк — мгновенный OOM. Требуется
**fast-path на уровне компаратора/merge-цикла**, плюс planner-поддержка.

## 6.4. Решения

### R-C9.1. Fast-path в merge-цикле: NULL-группа НИКОГДА не буферизуется

| Join | Поведение при достижении NULL-группы |
|---|---|
| INNER | NULL-хвосты **обеих сторон пропускаются за O(1)** (не могут дать строк): advance до конца — стриминг, ноль буферизации |
| LEFT | левый NULL-хвост **стримится с null-padding** (правая сторона не читается вовсе); правый NULL-хвост не трогается |
| RIGHT | зеркально LEFT (фаза 2) |
| FULL | обе стороны стримятся с padding независимо (фаза 2) |

Реализация: проверка `isNull(key)` в горячем цикле до compare (тот же guard-паттерн, что C1-NaN);
канонический порядок гарантирует контегуность хвоста — проверка дешёвая (только на границе
группы). Memory: O(1) независимо от размера хвоста.

### R-C9.2. Planner: `k IS NOT NULL` для INNER (добавляем сами)

Проверено: **авто-добавления IS NOT NULL к equi-join в Trino нет** (grep по planner/rules —
правила `*Null*` отсутствуют). Для INNER equi-join фильтр семантически эквивалентен
(NULL никогда не матчится) → `DetermineJoinAlgorithm` вставляет `k IS NOT NULL` в обе стороны:

- NULL-хвост отсекается **до shuffle** (меньше сети);
- pushdown в Iceberg: предикат `isNotNull` прунит файлы по метрике **null_count** в манифестах —
  файлы со 100% NULL в ключе skipping'аются целиком коннектором;
- для LEFT/FULL/RIGHT фильтровать нельзя (нужны null-padded строки) — работает R-C9.1.

### R-C9.3. Что НЕ является решением

- Бакетирование «по NULL отдельно» — не существует, NULL хэшируется константой (§6.1);
- сортировка NULLS_FIRST vs LAST — не влияет на размер группы, только на расположение
  (канонизация C3 уже требует единый порядок).

## 6.5. Тесты (в acceptance фазы 1/2)

- fuzz: NULL-доли {0, 1, 50, 95, 99, 100}% × join-типы × NULL-хвост 10⁹+ строк при малом пуле
  (`SMALL_MEMORY_POOL_BYTES`) — память оператора плоская (не растёт с хвостом);
- bucketed NULL-skew: обе таблицы bucket(k,N), 50% NULL → воркер с NULL-бакетом не OOM;
- план-тест: INNER SMJ-план содержит `IS NOT NULL` на обеих сторонах; LEFT — не содержит;
- oracle против hash join на всех NULL-долях.

## 6.6. Ответ на вопрос пользователя

**Да — в сегодняшнем hash/bucket мире весь NULL-хвост идёт в один бакет/воркер** (NULL_HASH_CODE
константен). SMJ решает это не распределением, а **стримингом**: INNER — O(1)-skip хвостов +
planner-фильтр `IS NOT NULL` (с прунингом файлов по null_count), LEFT/FULL — стриминг с
null-padding без буферизации группы. Дополнительно распределять NULL не нужно и нельзя
(семантика join).
