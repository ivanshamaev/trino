# 13. Кейс-стади: join 15 млрд × 17 млрд строк (несортированные входы, Java-реализация)

Сквозной разбор: какой план построит Trino, как выполнится SMJ, какие ресурсы нужны, где узкие
места и как сравнить с текущим hash join со спиллом. Velox не рассматриваем — только Java-путь,
спроектированный в документах 01-12.

## 13.1. Исходные допущения (параметрические)

| Параметр | Базовое значение | Комментарий |
|---|---|---|
| Строки | L = 15×10⁹, R = 17×10⁹ | |
| Ширина строки | 120 Б (join-ключ + payload) | варьируем 80-200 Б |
| Объём | L ≈ 1.8 ТБ, R ≈ 2.04 ТБ (raw) | до компрессии |
| Кластер | 50 воркеров × 32 ядра (1600 ядер), heap 96 ГБ | пример |
| Пул памяти/воркер | ≈ 70% heap ≈ 67 ГБ (`heap-headroom` 30%) | `LocalMemoryManager` |
| NVMe под спилл | 2 ТБ/воркер, ~2 ГБ/с sequential | лимит по умолчанию 100 ГБ — поднять |
| Сеть | 10-25 Гбит/с на воркер | |
| Selectivity | ключи в основном уникальны, 80-90% матчей | output ≈ 12-14×10⁹ строк |

Конфиг, обязательный к изменению (дефолты из кода): `query.max-memory` = **20 ГБ кластерно** —
поднять до ~2-3 ТБ; `max-spill-per-node` / `query-max-spill-per-node` = **100 ГБ** — поднять до
~1.5-2 ТБ; **spill выключен и пути не заданы**; компрессия спилла — включить `LZ4` (default `NONE`);
компрессия exchange — включить (`exchange-compression-codec`, default `NONE`);
`query_max_hash_partition_count` = 100 — поднять (см. 13.5).

## 13.2. План (по сценариям документа 11)

Возьмём худший распространённый случай **S8** (обе стороны непартиционированы) и лучший
несортированный **S1** (обе `bucket(k, 128)`):

```
S8 (полный shuffle):                          S1 (co-located, ноль exchange):
 Scan(L) → F/P → partialSort? → Ex(REPART,h(k))    Scan(L) → F/P → SortNode(спилл)
 Scan(R) → F/P → partialSort? → Ex(REPART,h(k))    Scan(R) → F/P → SortNode(спилл)
 JOIN-стадия (FIXED_HASH):                         JOIN-стадия (connector partitioning, 128 бакетов):
   merge(runs_L) ┐                                    merge(runs_L) ┐
   merge(runs_R) ┴→ MergeJoin → out                   merge(runs_R) ┴→ MergeJoin → out
```

MVP (без partitioned merging exchange): после `partitionedExchange` стоит обычный `SortNode`
(полная внешняя сортировка в join-задаче). Фаза 3: partialSort на скан-стадиях + merging exchange —
тогда join-задача только сливает потоки.

## 13.3. Объёмы и фазы (S8, базовые допущения)

| Фаза | Объём | Время (оценка) | Комментарий |
|---|---|---|---|
| 1. Скан из S3/Iceberg | 3.84 ТБ raw (~2 ТБ после Parquet-декомпрессии на wire не бывает — читаем raw) | 3.84 ТБ / (50 × 0.6 ГБ/с с NVMe-кэшем или 5 Гбит/с S3) ≈ **4-10 мин** | часто узкое место само по себе |
| 2. Shuffle (REPARTITION обеих сторон) | ~3.84 ТБ / компрессия LZ4 ~2× ≈ 1.9 ТБ на wire | 1.9 ТБ / 50 / 1.25 ГБ/с ≈ **30 с**; практичнее с накладными 1-3 мин | PagePartitioner → OutputBuffer → HTTP |
| 3. Спилл-сортировка (run generation) | запись 3.84 ТБ + чтение 3.84 ТБ на кластер (77 ГБ/воркер write+read) | 154 ГБ / 2 ГБ/с ≈ **77 с/воркер** + CPU сортировки | 1 проход, если ранов ≤ fan-in |
| 4. CPU сортировки | см. 13.4 | 2-6 мин wall (quicksort), 1-2 мин (radix) | параллелизм = числу join-задач |
| 5. Merge + join (стриминг) | чтение спилла слева+справа = повторное чтение 3.84 ТБ (если раны на диске) либо из памяти | ~77 с I/O + join CPU | sort-join fusion: фазы 3 и 5 совмещены — merge ранов льётся прямо в join, отдельного чтения нет |
| 6. Output | 12-14×10⁹ строк ≈ 1.7-2 ТБ | по downstream | |

**Ключевая оптимизация — sort-join fusion** (R5 из документа 12): не строить «отсортированную
таблицу», а k-way merge ранов каждой стороны подавать прямо в merge-join. Тогда суммарный
дисковый трафик = **1×write + 1×read** каждой стороны (только фаза 3), фаза 5 не читает диск.
I/O на воркер: 154 ГБ ≈ 77 с NVMe.

## 13.4. CPU-сравнение алгоритмов сортировки (наша инфраструктура vs radix)

Параметры: 100 hash-партиций → 32×10⁹ / 100 ≈ 320×10⁶ строк на партицию (160×10⁶ + 170×10⁶ на
стороны), N log₂ N ≈ 320×10⁶ × 28 ≈ 9×10⁹ сравнений на партицию.

| Подход | Стоимость/сравнение | Всего (32×10⁹ строк) | На 1600 ядер |
|---|---|---|---|
| Status quo: quicksort по адресам, random access в Blocks через компаратор | 40-100 ns (1-2 кэш-мисса) | ~9×10⁹×2 стороны... итого ~30-60 мин CPU | **~2-4 мин wall** |
| Flat-prefix + quicksort (сравнение long в кэше) | 10-20 ns | ~10-20 мин CPU | ~40-80 с wall |
| LSD radix 4×16-bit по (prefix,address) | без сравнений, 4 прохода × 16 Б/строку r+w sequential ≈ 15-25 ns/строку | ~10-15 мин CPU | **~25-45 с wall** |

Вывод: даже status quo допустим (сортировка ~2-4 мин wall на фоне 5-10 мин скана), radix даёт ~3-5×,
но не является блокером MVP. Основания для ожиданий — Spark-практика (radix в UnsafeExternalSorter)
и асимптотика; подтвердить JMH-микро (документ 07, §7.6).

## 13.5. Параллелизм: главное проектное ограничение

- Join-стадия FIXED_HASH: **задач = числу hash-партиций**; merge-драйвер = 1 на задачу (MVP).
- Default `query.max-hash-partition-count` = 100 → на 50 воркерах **2 задачи/воркер = 2 драйвера
  на 32 ядра** — сортировка и merge будут упираться в параллелизм, а не в I/O!
- `DeterminePartitionCount` всё равно даст 100 (rows-based 3200 упирается в max).
- **Рекомендации**: (а) для больших SMJ-join'ов поднимать `query_max_hash_partition_count`
  до 200-400 (4-8 задач/воркер — сортировка параллелится, memory pool делится между задачами —
  учесть в расчёте ранов); (б) в перспективе (фаза 2) — несколько merge-драйверов на задачу,
  каждый со своим подмножеством бакетов (partitionCount = k×taskCount, как обсуждалось в 08);
  (в) держать в уме `2×maxPossiblePartitionCount`-гвард в DeterminePartitionCount
  (при partitionCount близком к 2×(воркеры×concurrency) оптимизатор откажется от явного счёта).

## 13.6. Память и раны (математика ревокаций)

- Пул/воркер 67 ГБ; порог ревока 0.9, цель 0.5. Между join-задачами (4 шт. при 200 партициях)
  делёж ~16 ГБ на задачу; сортировочные буферы (revocable) двух сторон ~8 ГБ каждая.
- Раны: при 8 ГБ-буферах и 64 ГБ сортируемых на задачу (S8: 77 ГБ/воркер / 4 задачи ≈ 19 ГБ/задача
  на сторону... пересчёт: 3.84 ТБ / 200 партиций = 19 ГБ на партицию на обе стороны → L 9.3 ГБ +
  R 10.2 ГБ) → **1-2 рана на сторону** — merge тривиален (fan-in 2-3), проход по диску один.
- Худший случай: частые ревоки от соседних задач → много мелких ранов → работает каскад R4;
  счётчик ранов в статистиках оператора.
- Гигантская группа ключей (skew): память = окно правой группы; при 5% строк с одним ключом
  (750×10⁶ × 120 Б ≈ 90 ГБ) — обязателен SpillingMatchBuffer + block-nested-loop (05, §5.6);
  **но** вывод L×R при таких группах катастрофичен для любого алгоритма (750M×850M строк) —
  детекция по NDV-статистикам + warnings + (опционально) salting — это семантика запроса,
  а не реализация.

## 13.7. Сравнение с текущим hash join (spilling) на этом же кейсе

Сегодня Trino выполнит это как PARTITIONED hash join со спиллом (build = 17×10⁹ строк):

| Критерий | Hash join + spill (сегодня) | SMJ (проектируемый) |
|---|---|---|
| Shuffle | тот же (обе стороны по k) | тот же |
| Структура build | хэш-таблица 17×10⁹ строк (≈2-3× данных = 4-6 ТБ на кластер) — **в память не влезает никогда** | нет хэш-таблицы: сортированные раны на диске + курсоры |
| Спилл-проходы | спилл обеих сторон по партициям + **повторные проходы** при переполнении партиции (spillEpoch, пересборка LookupSource, повторное чтение probe-страниц) — риск 2-3× I/O при неудачном раскладе | ровно 1×write + 1×read каждой стороны (fusion) |
| Память | revocable под индекс + партиции; пик = самая большая спилл-партиция при load | окно группы + k буферов merge — **прогнозируемо мало** |
| CPU | N хэшей build + N×(1-2) lookup'ов (random) + повторные хэши при spill-эпохах | N log N сравнений (или radix O(N)) + линейный merge (sequential) |
| Skew-устойчивость | hot-ключ раздувает одну партицу → многократный spill; build-outer (RIGHT/FULL) **не спиллится вообще** | память = макс. группа (bounded, спиллится); skew-вывод — общая проблема обоих |
| RIGHT/FULL | только в память (без спилла) — на 17×10⁹ строк нереалистично | работает тем же механизмом |
| Pre-sorted входы | не помогает | сортировка элитируется (Iceberg sort order) |

Вывод: на 15B×17B **текущий путь практически нежизнеспособен без многократного спилла**, SMJ даёт
гарантированно один проход по диску и bounded memory — это и есть обоснование фичи.

## 13.8. Сквозной профиль ожиданий (S8, 50×32 ядер, при CBO-конфиге из 13.1)

```
T+0    скан из S3 (3.84 ТБ, параллельно с shuffle по мере готовности страниц)
T+6м   shuffle завершён; join-задачи получают партиции по 19 ГБ
T+6м   run generation: сортировка буферов по мере ревоков, спилл на NVMe (одновременно стримится probe)
T+8м   merge-fusion: k-way merge ранов обеих сторон → merge join → output стримом
T+10м  output ~13×10⁹ строк в downstream (exchange/запись)
Итого: ~10-12 минут, лимитировано сканом и I/O, память bounded (~16 ГБ/задача),
       без OOM-риска при любом раскладе ключей (кроме патологического вывода).
```

(Числа — инженерные оценки для планирования; подтвердить синтетическим бенчмарком
1×10⁹ → 1×10¹⁰ → масштаб, документ 07, §7.6.)

## 13.9. Чек-лист внедрения для этого кейса

1. Спилл: пути на NVMe, `spill-compression-codec=LZ4`, лимиты ≥ объёма данных/2 на воркер.
2. `query.max-memory` ≥ 2 ТБ (кластерно), `query_max_hash_partition_count` = 200-400.
3. `join_distribution_type=PARTITIONED` (детерминизм), `colocated_join=true`.
4. Таблицы: если возможно, `partitioning = bucket(k, N)` на обе стороны (S1 — ноль shuffle) —
   идеальный ETL-паттерн: писать в bucketed+sorted таблицы (`sorted_by` уже поддерживается
   write-путём) → следующий join получит и ноль exchange, и ноль сортировки.
5. Мониторинг: `JoinStatisticsCounter` + гистограммы групп; раны/спилл-байты в OperatorStats;
   NDV join-ключа до выполнения (манифесты + puffin NDV) для skew-предупреждений.

## 13.10. Открытые вопросы кейса

1. Как масштабируется генерация ранов при **конкуренции задач** (4 задачи × 2 стороны делят пул):
   ревоки частые и мелкие → каскад-merge обязателен уже в MVP? (проверить синтетикой).
2. Асинхронный доп. спилл в finish() (TODO кода) — при 19 ГБ/сторону хвост без ревока не влезет.
3. Мержить ли частично на стороне отправителя (partialSort + partitioned merging exchange, R6) —
   переносит сортировку на скан-стадии, join-задача без спилла; требует фазы 3 синтеза.
4. Влияние `PagePartitioner`-порядка: строки приходят в exchange-порядке (примерно по хэшу от
   нескольких отправителей) — «почти сортированные» вставки (timsort-подобная адаптивность?)
   не планируется, но измерить «адаптивность» quicksort на таких данных стоит.
5. Правильный порог «SMJ vs grace-hash-подобный спилл-hash-join» в cost-модели при полностью
   несортированных входах: сортировка N log N vs повторные спилл-проходы hash — подобрать
   на синтетике (кандидат: SMJ если build > K× доступной памяти, K ≈ 1.5-2).
