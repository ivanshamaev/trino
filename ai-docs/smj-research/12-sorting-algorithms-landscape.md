# 12. Ландшафт алгоритмов сортировки и их наличие в Trino

Контекст: SMJ для 15 млрд × 17 млрд строк на несортированных входах требует **внешней сортировки
десятков ГБ на воркер**. Документ: (а) какие алгоритмы существуют в индустрии/литературе,
(б) что реально есть в Trino (проверено grep'ом по коду), (в) рекомендации. Реализация — Java,
Velox не рассматриваем.

## 12.1. Требования к сортировке в нашем кейсе

1. **Внешняя** (данные ≫ памяти), с bounded memory и ревокацией (revocable memory + MemoryRevokingScheduler).
2. **Параллельная** — по партициям/baket'ам как минимум; желательно внутри одной партиции.
3. Сортировка **только по join-ключу** (1..N колонок), не по payload.
4. Устойчивость к skew (гигантские группы равных ключей — это нормально для сортировки,
   проблема только для join-вывода).
5. Желательно: **order-preserving кодирование ключа** (для radix-сортировки, быстрого merge,
   компактного спилла).
6. Интеграция со стримингом: отсортированные раны должны **лениво вливаться в merge-join**
   без материализации «отсортированной таблицы».

## 12.2. Обзор алгоритмов

### 12.2.1. Сравнительные in-memory сортировки
- **Quicksort** (Bentley–McIlroy, 3-way partition): O(N log N) в среднем, отличный cache-паттерн
  при сортировке массива указателей/адресов; не стабилен; деградация на равных ключах лечится
  3-way partition (у Trino есть).
- **Timsort / stable mergesort**: стабильность для нас не критична (порядок равных ключей
  семантически не важен), O(N log N) всегда, но больше проходов по памяти.
- **Parallel sort** (`Arrays.parallelSort`, fork/join split + parallel merge): существует в JDK,
  но в однодрайверной операторной модели Trino не применим напрямую (нужна своя декомпозиция).

### 12.2.2. Несравнительные (radix/counting)
- **LSD radix sort** по 8-байтовому order-preserving префиксу ключа: O(k·N) (k = число проходов,
  обычно 8×8 бит или 11×6 бит), без сравнений, идеально sequential access, SIMD-дружелюбен.
  Промышленное доказательство: Spark `UnsafeExternalSorter` сортирует массив пар
  `(pointer, prefix)` (16 Б/строку) radix'ом (fallback TimSort), где prefix — order-preserving
  кодировка первой части ключа; коллизии префикса дорезолвированы компаратором.
- **MSD radix / radix clustering** (HyPer, Polychroniou et al. «Comprehensive Study of Main-Memory
  Parallel Partitioning»): распределение по старшим цифрам — одновременно сортирует (по цепочке
  цифр) и партиционирует; в БД чаще используется как «radix clustering» перед hash join.
  Для SMJ интересно: **наш join и так hash-партиционирует по join-ключу** — radix-проход по
  ключу на этапе партиционирования давал бы «отсортированные заодно» партиции.

### 12.2.3. Внешние сортировки (главное для нас)
- **Классический external merge sort**: фаза генерации ранов (in-memory sort буфера → spill
  отсортированного рана) + фаза слияния (k-way merge). Число проходов по данным =
  ⌈log_F(N/run)⌉ + 1, где F — merge fan-in. При run ≈ доступной памяти и F ≥ N/run — **один
  проход слияния** (запись + чтение каждого байта ровно один раз).
- **Replacement selection** (Knuth Vol.3, куча размера M): раны в среднем **2×M** — меньше ранов
  и меньше слияний; но heap-перестроение = плохая локальность, каждая вставка ~ log M случайных
  доступов. Современный консенсус (Graefe, «External Sorting» в Modern B-Tree Techniques;
  практика PostgreSQL/Spark): quicksort-раны почти всегда быстрее на практике; replacement
  selection остаётся интересным при **поточном входе** (мы получаем страницы из exchange —
  вход потоковый!) для генерации более длинных ранов без полного буфера.
- **Каскадное слияние с ограниченным fan-in**: пока ранов > F, мержатся самые маленькие группы
  (cascade/overlay-merge) — bounded память при любом числе ранов. Есть в Hive
  `SortingFileWriter.combineFiles` (мержит файлы, пока `tempFiles.size() > maxOpenTempFiles`).
- **Radix/bucket external sort**: вместо «сортировать буфер → spill», разложить буфер по
  F корзинам по цифре ключа и spill'ить корзины; при достаточной глубине рекурсии корзины уже
  отсортированы (сортировка = партиционирование, сравнений нет вообще). Требует order-preserving
  ключа и известного бюджета: глубина ⌈bytes/bits_per_pass⌉, память = F выходных буферов.
- **Sort-fusion с потребителем**: раны не «склеиваются в файл», а **лениво k-way мержатся прямо
  в потребителя** (наш merge-join). Экономит полный проход записи объединённого вывода. У Trino
  это уже почти так: `OrderByOperator` стримит merged output лениво (но копирует через PageBuilder).

### 12.2.4. Параллельные/распределённые схемы
- **PSRS** (parallel sorting by regular sampling): семплирование → выбор pivots → range-разбиение
  → локальные сортировки → финальный merge. Дает **глобально упорядоченные партиции** — ровно то,
  что нужно «partitioned merging exchange» (фаза 3 синтеза).
- **Range partitioning по статистикам**: вместо семплирования — Iceberg min/max по файлам/манифестам
  (есть бесплатно в `TableStatisticsReader`/манифестах) как приближенную гистограмму ключа;
  лечит hot-bucket skew (сравни ClickHouse `query_plan_join_shard_by_pk_ranges`).
- **MergePath** (O(n/s + s·log s) декомпозиция параллельного слияния) — для многопоточного
  финального merge внутри одной партиции (если один merge-драйвер на бакет станет узким местом).

### 12.2.5. Альтернатива сортировке: grace hash join
Рекурсивное разбиение обеих сторон на партиции, влезающие в память, затем hash join per партиция.
Сортировка не нужна вовсе (O(N) хэшей на проход). У ClickHouse — `grace_hash` (и auto-fallback
hash→grace). В Trino текущий spilling hash join функционально близок (спилл-партиции обрабатываются
по одной). Честное сравнение с SMJ для 15B×17B — в документе 13; кратко: SMJ выигрывает по
предсказуемости (1 проход слияния vs риск многократных проходов), проигрывает по CPU на
сортировке (N log N сравнений vs N хэшей) при полностью несортированных входах.

## 12.4. Точная механика существующей внешней сортировки (OrderByOperator)

`core/trino-main/.../operator/OrderByOperator.java` + `spiller/*`:

- **Накопление**: `addInput → PagesIndex.addPage` (страницы в `ObjectArrayList<Block>[]`,
  адреса строк в `LongArrayList`); память — **revocable** (кандидат на ревокацию).
- **Генерация ранов**: `startMemoryRevoke → spillToDisk`:
  1. сортируется **весь текущий индекс** (quicksort по адресам — каждый compare это random access
     в блоки через скомпилированный `BLOCK_POSITION`-компаратор);
  2. `spiller.spill(pageIndex.getSortedPages())` — **ран = всё, что накопилось к моменту ревока**
     (не кратно буферу; размер определяется тем, сколько успело набраться до 90% пула);
  3. индекс очищается, набор продолжается. Число ранов = число ревоков — не ограничено.
- **Финал (`finish`)**: конвертация revocable→user (при неудаче — **синхронный** доп. спилл, TODO
  «should be asynchronous» в коде); сортировка остатка; если ранов нет — ленивый итератор по индексу,
  иначе `mergeSortedPages(все spill-раны + остаток)` через PriorityQueue.
- **Вывод**: ленивый (по странице на `getOutput`), **но через PageBuilder с полным копированием**
  строк в новые страницы (~1 MiB); индекс держится до `close()`.
- **Fan-in**: не ограничен (сколько ранов — столько входов кучи; память = по 1 странице на вход + буфер вывода).
- **Спилл-файлы**: 1 файл на ран (продакшн-путь `GenericSpiller`); запись через 4 KiB-буферы;
  **чтение одноразовое**; round-robin по spill-путям с проверкой свободного места (>10%).
- **Дефолты**: `max-spill-per-node=100 GB`, `query-max-spill-per-node=100 GB`,
  **компрессия спилла `NONE`** (есть LZ4/ZSTD), spill по умолчанию выключен и пути не настроены;
  ревоки: порог 0.9 пула, цель 0.5; пул памяти = heap − 30% headroom (~70% heap);
  `query.max-memory` (кластерно) = **20 GB** — для ETL надо поднимать.

## 12.5. Анализ: достаточно ли существующего для 15B×17B?

**Достаточно для работоспособности (MVP), недостаточно для производительности:**

| Свойство | OrderByOperator как есть | Нужно для 15B×17B |
|---|---|---|
| Корректность внешней сортировки | ✅ | ✅ |
| Число проходов по диску | 1 запись + 1 чтение (при раны ≤ fan-in) — ✅ | то же |
| Стоимость сравнения | random access в блоки, ~десятки ns; N log N сравнений | нужен flat-префикс + radix (без сравнений) или хотя бы prefix-компаратор |
| Копирование вывода | полный дубль через PageBuilder | словарный вывод / слияние прямо в join (без пере-материализации) |
| Fan-in | неограничен (куча деградирует на сотнях входов) | каскад при >64 |
| Параллелизм | 1 драйвер на партицию | партиций достаточно (100+), внутри — при необходимости MergePath |
| Ревокация/память | ✅ revocable + синхронный доп. спилл | асинхронный доп. спилл (TODO в коде) |

Оценка CPU-разницы (детали в 13): quicksort по адресам с random access ≈ 40-100 ns/строку на
миллиардных партициях; radix по flat-префиксу ≈ 10-25 ns/строку (8 проходов × 16 Б/строку
sequential). На 32 млрд строк суммарно это разница между ~20-50 и ~5-13 минутми на 1600-ядерном
кластере — заметно, но не блокирует MVP.

## 12.6. Рекомендации (Java, по фазам)

**R1 (MVP, переиспользование — ноль новой сортировочной логики):**
`SortNode` над каждым входом + существующий `OrderByOperator` (внешняя сортировка уже
корректна: 1 проход генерации ранов + ленивый k-way merge). Join-оператор потребляет
`getSortedPages`-подобный поток. Учесть: включить спилл + пути + LZ4; поднять лимиты.

**R2 (фаза 1.5, инфраструктурная): order-preserving кодировка ключа** — новый компонент
`JoinKeyNormalizer`: для BIGINT `long ^ 0x8000...` (знак→беззнак), INT/SMALLINT аналогично,
DOUBLE — total-order кодировка (IEEE переупорядочение: flip sign bit / invert negatives),
DECIMAL(≤18) — как long со знаком, TIMESTAMP — как long, VARCHAR — первые ≤8 байт UTF-8
(+0x01-паддинг, fallback на полный компаратор при равенстве префикса), multi-column —
конкатенация до 8 байт + tiebreak. Переиспользовать `TypeOperators` (значения), чанки
`VariableWidthData` — для длинных ключей. Это разблокирует R3 и ускоряет merge.

**R3 (фаза 2): LSD radix sort по `(prefix, address)`-парам** для fixed-width ключей
(Spark-паттерн): сортировка = 8 проходов counting-распределения 16-битовых корзин (4 прохода) или
8-битовых (8 проходов) по 16-байтовой паре; fallback на quicksort для переменноширинных/широких
ключей и при малых N (< ~1M строк). Ожидание: 2-4× к фазе сортировки.

**R4 (фаза 2): каскадный merge с fan-in ≤ 64** по образцу `SortingFileWriter.combineFiles`
(перенести в core) — bounded память и предсказуемая производительность при любом числе ранов;
актуально, если ревоки частят и ранов сотни.

**R5 (фаза 2): sort-join fusion**: раны каждой стороны k-way мержатся **прямо в merge-join**
без сборки объединённого отсортированного потока (это уже почти так у OrderByOperator —
убрать PageBuilder-копирование, отдавать join'у курсоры над рандом-адресами исходных страниц).

**R6 (фаза 3): частичная сортировка + partitioned merging exchange** (S1/S4/S7 сценарии):
сортировка на скан-стадии по сплитам → REPARTITION+merging exchange → join-задача только мержит;
плюс range-разбиение по Iceberg min/max как анти-skew (вместо hash, по образцу ClickHouse PK-ranges).

**Чего НЕ делать**: replacement selection (локальность хуже, выигрыш только при экстремально
малых буферах), `Arrays.parallelSort` (не вписывается в драйверную модель), MSD radix как
основной путь (сложность управления глубиной при переменной ширине; LSD проще и доказан Spark).

## 12.7. Открытые вопросы

1. Асинхронный доп. спилл в `finish()` OrderByOperator (TODO в коде) — при большом хвосте ранов
   блокирует драйвер; нужен для SMJ обязательно.
2. Кеш скомпилированных компараторов при R2/R3: префикс-коллизии → полный компаратор — счётчик
   коллизий в статистиках оператора (для выбора ширины префикса).
3. Двойной учёт памяти при sort-join fusion (раны держатся join'ом, а не сортом) —
   memory-context transfer.
4. Стоит ли делать radix-партиционирование обменом (sort during shuffle) — т.е. PagePartitioner
   пишет в партиционные буферы уже упорядоченно по префиксу — тогда merge на приёмнике принимает
   k упорядоченных потоков без локальной сортировки вообще (сближается с R6, но требует
   сортировки партиционных буферов на отправителе — цена: сортировка всё равно есть, просто
   на другой стадии; выгода — join-стадия без спилла).
