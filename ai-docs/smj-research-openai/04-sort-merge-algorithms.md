# Алгоритмы и модель ресурсов

В этой главе приведён алгоритмический анализ и проектные выводы. Обзор конкретных реализаций и первичных источников находится в [05](05-other-engines.md).

## Merge уже отсортированных входов

Для equijoin по составному ключу `K=(k1,...,kd)` оба входа должны иметь одинаковое лексикографическое направление, null ordering и совместимую семантику типов. Если текущий левый ключ меньше правого, левую строку можно пропустить для INNER или выдать с NULL для LEFT. При равных sort keys необходимо обработать **группы**, а не одну пару строк.

Для comparator-equivalence group `k` с `a_k` строками слева и `b_k` справа имеется `a_k*b_k` пар-кандидатов. Столько же строк выдаёт INNER без residual, только если equality истинно для всех пар группы: NULL и NaN показывают, почему это условие нельзя опускать. При residual predicate все пары могут потребоваться для проверки, даже если фактический результат мал. Поэтому:

```text
C = Σ_k a_k * b_k                 # число пар-кандидатов
Z = число реально выданных строк  # Z ≤ C для INNER
T_merge = O(N + M + C)            # при константной стоимости сравнения/фильтра
```

`O(N+M)` допустимо лишь при дополнительных предпосылках, например уникальности хотя бы одной стороны и ограниченной стоимости output. Длинные составные/строковые ключи добавляют стоимость comparator. Никакой алгоритм не выведет `10^12` строк за время, независимое от этого объёма.

## Группы совпадений и replay

Простой вариант: материализовать правую группу, для каждой левой строки снова сканировать её. Это корректно для INNER/LEFT, если сохраняется флаг «для этой левой строки найден match после residual». При наличии spill memory ограничивается несколькими страницами, но disk reread может быть очень велик.

Лучший следующий вариант — tile-based product: удерживать bounded tile левых строк, проходить правую группу, затем переходить к следующему tile. При `Q` фактических tiles и размере правой группы `B` объём её полных повторных чтений составляет примерно `Q*B`. Для левой группы размером `A` и tile budget `T` идеализированная оценка при плотном заполнении — `ceil(A/T)*B`; это не верхняя граница при variable-width rows и недозаполненных tiles. Оценка относится к replay, не ко всем I/O запроса. Для LEFT потребуется matched bit на строку текущего tile; для FULL — persistent matched-state правой группы с собственным paging/spill.

Выбор меньшей группы для буферизации полезен, но её размер не всегда известен до конца. Для MVP фиксированная буферизуемая сторона уменьшает сложность. Специальный путь при доказанной uniqueness может вообще обходиться без replay. «Статистика NDV примерно равна rows» не является доказательством uniqueness для корректности.

## External merge sort

Run generation:

1. Читать projected pages до byte budget, учитывая retained size и запас под сортировку/запись.
2. Сортировать bounded `PagesIndex` по каноническому ключу.
3. Сохранить run на диск; освободить данные только после подтверждения записи и передачи ownership.
4. Повторить. Счётчики общего объёма и числа строк должны быть 64-битными, даже если одна page/index использует int positions.

Run merging: одновременно читать не более `F` runs. Если runs больше, выполнять промежуточные merge passes. Последний merge можно подавать непосредственно в join, без записи ещё одного полного sorted file.

Для стороны размером `D` байт, рабочего run budget `B`, `R=ceil(D/B)` и fan-in `F≥2`:

```text
P = ceil(log_F(R))                       # R > 1
merge-reader memory ≈ F * reader_budget + heap/cursors + output
temporary I/O ≈ 2 * P * D                # идеальная схема, final merge streamed
```

Последняя формула включает запись initial runs, чтения и промежуточные записи; не включает source scan, shuffle, compression ratio, duplicate replay и дополнительную полную материализацию. Для одного spilled run примерно `2D`; для полностью in-memory пути temporary I/O равен нулю. Фактические значения должны измеряться. С увеличением `F` уменьшается число проходов, но растут память, descriptors и read concurrency.

Пример расчёта, **не benchmark**: `D=100 GiB`, `B=256 MiB` дают около 400 runs. При `F=16` нужны три merge levels; идеализированный temporary I/O составляет около `600 GiB` на сторону. Материализация финального потока до чтения join увеличит это число. Так объясняется, почему SMJ может экономить RAM и одновременно быть медленнее hash join.

Нужно ограничивать не только readers: список миллионов run descriptors тоже может расти без bound. Возможные решения — online compaction с отдельным лимитом resident metadata и disk-backed manifest; одно лишь увеличение числа compaction levels не доказывает постоянную память. Число одновременно открытых файлов ограничивается отдельно. При multipass merge прежние runs удаляются только после успешного завершения и фиксации нового run, иначе отмена/ошибка записи приводит к потере данных или утечке.

## Распределённый SMJ

Рекомендуемый старт — hash repartition **обоих** входов по одним join keys, затем sort внутри каждой соответствующей partition и локальный merge. Глобальная сортировка не нужна. Hash здесь используется для маршрутизации, а не для build lookup, поэтому partition может превышать RAM.

Range partitioning — альтернативный путь: одинаковые границы ranges на обеих сторонах, затем local sort/merge. Он полезен для range predicates и дальнейшего ordered processing, но требует sampling, общих границ и правил для ключей на границе. Разрезать одинаковый join key между partitions без replication и ownership protocol некорректно.

Hot key не исчезает после hash или range repartition. Для его параллельной обработки можно разбить одну группу на tiles и реплицировать другую либо разбить Cartesian grid групп. Это отдельный skew protocol с учётом outer unmatched rows и exactly-once pair ownership. В MVP — bounded spill и диагностика hot keys; равномерную latency для таких данных обещать нельзя.

## Варианты, которые не следует смешивать

| Вариант | Сильная сторона | Главная цена/ограничение |
|---|---|---|
| Full external SMJ | Последовательные passes, обе стороны могут превышать RAM | Сортировка обоих входов |
| Merge presorted streams | Нет run generation при доказанном порядке | Нужен порядок полного потока после exchanges |
| Partial merge | Полный sort одной стороны, sort batches другой | Повторные чтения overlapping ranges |
| External/radix hash | Не сортирует все строки | Hash partitioning, skew и управление памятью |
| In-memory SIMD/MPSM | CPU/cache/locality на подходящих данных | Сам по себе не решает external memory и Trino lifecycle |

Общая рекомендация: сначала bounded full external SMJ; partial merge и range partitioning оценивать отдельными экспериментами. Улучшение external hash остаётся полезным конкурирующим направлением, а не исключается постановкой задачи.
