## 3. Реализуемость каждого пункта (по этапам)

- **Stage 0** — реализуем: все API на месте (план файлов, sortOrderId, SortFieldInfo,
  SortingProperty/SPI не меняется). Единственная нетривиальная часть — консервативный критерий
  (проверка ВСЕХ файлов после прунинга) — алгоритмически прямая.
- **Stage 1** — реализуем: механика @JsonCreator без перегрузок подтверждена прецедентами
  (`spillable`, `maySkipOutputDuplicates`); 45 мест — механический рефакторинг под контролем
  компилятора; прецеденты тестов есть.
- **Stage 2** — реализуем: адаптер-фабрика и JoinBridge-контракт подтверждены; NaN/NULL-guards —
  локальная логика автомата; MatchBuffer + residual — контракт `JoinFilterFunctionFactory` (:257)
  подходит (адреса build через PagesIndex/MatchBuffer — I8 проработан).
- **Stage 3** — реализуем: правило — стандартный iterative-rule; все гварды — точечные skip'ы в
  существующих правилах; property-рецепт 03 §3.3 точен.
- **Stage 4** — реализуем: LOCAL merging — готовый паттерн visitSort; SortNode-в-стадии —
  AddLocalExchanges обрабатывает (fixedParallelism + merging, без новых фрагментов — I7);
  DF-обёртка — готовый вызов. Нюанс (контур сложности): MERGE-ветка строит SortNode сама и
  выводит свойства напрямую (не через повторный plan SortNode), чтобы не получить
  дополнительный remote merging exchange от visitSort — паттерн `withDerivedProperties` в
  AddExchanges для этого существует.
- **Stage 5** — реализуем по частям; спилл-группы опираются на существующий Spiller-стек;
  outer-streaming — анализ risks/07 не требует новых механизмов движка; multi-driver —
  JoinBridgeManager уже многозадачный (probeFactoryCount).
- **Stage 6** — реализуем: ослабление 4 checkArgument — локальная правка + фабрика; cost —
  по образцу существующего static-метода; фрагментер правок не требует (подтверждено).
- **Stage 7** — пункты сформулированы как research-мини-планы (P12 явно помечен spike'ом) —
  реализуемость оценивается в каждом мини-плане (соответствует фазе 4 плана 04).
